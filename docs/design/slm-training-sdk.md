# Domain Intelligence Platform Design

## Purpose

Design a reusable compiler platform for building, validating, packaging, and deploying domain intelligence for small models. The first experiment is the Indian food menu assistant, but the same framework must support finance QA, Java/Sonar review, federated enterprise search, prompt enhancement, release-aware database querying, and future domain packs.

This should not be treated as a generic "SLM training SDK." Training is only one stage. The platform compiles domain knowledge into deployable AI capabilities.

The platform should make each use case a set of knowledge packs, adapter packs, and runtime packs with consistent lifecycle stages:

```text
knowledge source
  -> transformation
  -> dataset
  -> adapter training
  -> evaluation
  -> packaging
  -> deployment
  -> inference
```

The core compiler model:

```text
Knowledge Sources
  -> Knowledge Compiler
  -> Domain IR
  -> Optimization
  -> Artifact Generation
      -> Adapter Packs
      -> Runtime Packs
      -> Prompt Packs
      -> Knowledge Graph
      -> Embeddings
      -> Benchmarks
      -> Documentation
      -> APIs
      -> Validators
```

## Design Principles

- Knowledge packs and adapter packs, not one monolithic model.
- The v1 core must stay small and stable; everything else is a plugin or generator.
- The three immutable abstractions are `Knowledge`, `Domain IR`, and `Artifacts`.
- Nothing bypasses Domain IR.
- Generated artifacts should be one of four first-class types: Knowledge Pack, Blueprint Pack, Adapter Pack, Runtime Pack.
- Structured outputs first; conversational prose second.
- Local-first and privacy-safe by default.
- Deterministic datastore remains the source of truth.
- SLM routes, extracts, formats, and explains; it does not own facts.
- Every trained model must have task-specific validators.
- Fine-tuning is optional; blueprint prompting and template search should be tried first.
- PEFT adapters are the primary adaptation artifact.
- Full model training is out of scope for normal use.
- Domain IR is the stable contract between knowledge sources and generated artifacts.
- Safety policies are explicit domain artifacts, not hidden prompt text.
- Runtime packaging must support small local models, including sub-500 MB artifacts where required.
- Capabilities should be reusable across domains.
- Every lifecycle stage should be a replaceable pipeline plugin.
- Domain data and training data must remain separate artifacts.
- The SDK must be runtime-agnostic and model-agnostic.
- Publishing targets should be plugin-based.
- Every stage should be resumable and cache its output.
- Deterministic stages and AI stages must be separated for reproducibility.
- Generated artifacts are immutable and versioned.

## V1 Core Invariants

These are the architecture boundaries to freeze for v1.

### 1. Three Immutable Abstractions

```text
Knowledge
  -> Domain IR
  -> Artifacts
```

All compilers, generators, validators, packagers, and runtimes consume Domain IR. No stage should bypass it by reading raw source data directly after compilation.

### 2. Four First-Class Artifact Types

Everything generated by the platform should be one of:

- Knowledge Pack
- Blueprint Pack
- Adapter Pack
- Runtime Pack

Other outputs belong inside one of these packs or are generated from them:

- benchmarks
- prompts
- validators
- documentation
- datasets
- metadata
- runtime configs

### 3. Stable Compiler Pipeline

```text
Knowledge Sources
  -> Parser
  -> Normalizer
  -> Resolver
  -> Validator
  -> Domain IR
  -> Optimizer
  -> Artifact Generator
```

Do not add new core stages unless the invariant breaks. New functionality should usually be a compiler pass, artifact generator, validator, backend, or plugin.

### 4. DDL as the Authoring Format

Domain Definition Language should become the single authoring format for domain intelligence.

Example:

```yaml
domain: food

entity:
  Dish

attributes:
  - ingredients
  - allergens
  - nutrition

relationships:
  contains:
    target: Ingredient

policies:
  - allergen_disclaimer

capabilities:
  - conversation
  - retrieval
  - tool_calling
```

From DDL, the compiler can generate:

- JSON Schema
- validators
- synthetic datasets
- documentation
- prompts
- Domain IR
- benchmarks
- adapters
- runtime assets

### 5. Model Backend Interchangeability

The compiler should target capability contracts, not specific model families. Qwen, Gemma, Phi, Llama, Mistral, or future models are backend implementations.

```text
ModelBackend
  -> Qwen
  -> Gemma
  -> Phi
  -> Llama
  -> Mistral
```

No domain pack should require code changes when the backend model changes.

### 6. Runtime ABI

Applications depend on a runtime ABI, not a specific runtime implementation.

```text
generate()
embed()
extract()
classify()
tool_call()
rerank()
stream()
```

Every runtime adapter implements this ABI.

### 7. Versioned Public Domain IR

Domain IR must be public and versioned:

```text
Domain IR v1
Domain IR v2
Domain IR v3
```

Stable IR compatibility allows new compiler versions while preserving existing packs.

### 8. Verification Before Validation

Separate structural correctness from quality measurement.

Verification:

- schema
- references
- policies
- relationships

Validation:

- benchmarks
- accuracy
- latency
- memory
- hallucination rate

A pack should fail early during verification before any adapter training or benchmarking.

### 9. Reproducible Lineage

Every generated artifact records its parents:

```text
Knowledge Pack
  -> Domain IR
  -> Blueprint Pack
  -> Dataset
  -> Adapter Pack
  -> Runtime Pack
```

The platform must be able to answer which source knowledge, IR version, blueprint, dataset, adapter, runtime target, SDK version, and commit produced any artifact.

### 10. Compiler Targets Beyond SLMs

The long-term platform remains centered on domain intelligence, not only language models. Future artifact generators can produce:

- retrieval indexes
- embedding collections
- knowledge graphs
- APIs
- documentation sites
- MCP-compatible tools
- agent tool specifications

These are compiler targets generated from Domain IR.

## V1 Phase Scope

Architecture expansion should stop here. The next milestone is a reference implementation that proves the compiler model.

### Phase 1: Domain Intelligence Compiler

Implement only the compiler infrastructure:

```text
Knowledge Sources
  -> Parser
  -> Normalizer
  -> Resolver
  -> Validator
  -> Domain IR
  -> Optimizer
  -> Artifact Generator
```

Phase 1 deliverables:

- DDL parser
- Domain IR specification
- Knowledge Pack compiler
- Blueprint Pack generator
- JSON Schema generation
- documentation generation
- validator generation
- compiler manifest generation

No model training in Phase 1.

### Phase 2: Adapter Pipeline

After the compiler is stable:

```text
Domain IR
  -> Synthetic Dataset
  -> Prompt Pack
  -> LoRA Training
  -> Evaluation
  -> Adapter Pack
```

Only PEFT should be supported initially. Avoid full fine-tuning, distributed training, RLHF, DPO, and continual pretraining in v1.

### Phase 3: Runtime

```text
Adapter Pack
  -> Runtime Pack
  -> Inference ABI
```

Initial runtime support should be limited to:

- llama.cpp
- Ollama
- Transformers

### Phase 4: Registry

Only after compiler and runtime are stable:

```text
Knowledge Packs
Blueprint Packs
Prompt Packs
Adapter Packs
Runtime Packs
```

Everything becomes installable through the registry.

### Compiler Manifest

Every compilation should produce a compiler manifest separate from runtime artifact manifests:

```yaml
compiler:
  version: 1.0.0

knowledge_pack:
  id:
  version:

ddl:
  version:

domain_ir:
  version:

artifacts:
  blueprint:
  adapter:
  runtime:

build:
  timestamp:
  git_commit:
```

The compiler manifest records the compilation process itself, making builds deterministic and reproducible.

## Non-Goals

- Building a generic ChatGPT clone.
- Training one model to memorize every dataset.
- Full model training from scratch.
- Directly executing unsafe automation commands from model output.
- Letting SQL or hardware payloads bypass validation.
- Treating synthetic data as trusted without filtering and evaluation.

## Core SDK Concepts

### Domain IR Specification

Domain IR should be an official platform contract, not merely an internal data structure.

```text
Knowledge Sources
  -> Parsers
  -> Domain IR
  -> Consumers
```

Every downstream system should consume Domain IR:

- synthetic dataset generator
- documentation generator
- benchmark generator
- adapter trainer
- embedding generator
- runtime packager
- API generator
- knowledge graph exporter
- validator generator

Domain IR is the platform equivalent of LLVM IR: a stable intermediate representation from which many optimized artifacts can be generated.

### Compiler Passes

The platform should use compiler passes rather than a hardcoded linear pipeline. Each pass has one responsibility.

Pass sequence:

```text
Parser
  -> Normalizer
  -> Resolver
  -> Validator
  -> Optimizer
  -> Domain IR
  -> Artifact Generation
```

Example food import:

```text
CSV or Excel
  -> entity resolution
  -> duplicate removal
  -> terminology normalization
  -> relationship expansion
  -> policy injection
  -> Domain IR
```

Passes should be individually runnable, cacheable, and testable.

### Domain Definition Language

The platform should introduce a Domain Definition Language for authoring domain intelligence at a higher level than raw JSON.

Example:

```yaml
entity: Dish

attributes:
  - calories
  - allergens
  - ingredients

relationships:
  contains:
    target: Ingredient

validators:
  - allergen_check
```

The compiler should generate from DDL:

- JSON schemas
- validation logic
- synthetic examples
- documentation
- embeddings
- training datasets
- knowledge graph definitions
- API contracts

DDL is a major differentiator because it makes domain intelligence declarative and compilable.

### Artifact Immutability

Generated artifacts should be immutable. Do not overwrite prior builds.

Artifact layout:

```text
knowledge/
  food/
    1.0.0/
    1.1.0/
    2.0.0/
datasets/
adapters/
runtime/
benchmarks/
```

Each artifact version should include a manifest and provenance record. Rollback should mean selecting a previous immutable artifact, not reconstructing it from memory.

### Registry Layer

The platform should have a registry layer for more than models.

Registry artifact types should be centered on the four first-class packs:

- Knowledge Packs
- Blueprint Packs
- Adapter Packs
- Runtime Packs

Plugins and connectors can also be registered, but they are platform extensions rather than generated domain artifacts.

Future CLI shape:

```bash
dip install food-pack
dip install restaurant-pack
dip install allergen-blueprint-pack
dip install qwen-runtime
```

The registry enables composition from reusable artifacts.

### Capability Contracts

Domain packs and artifacts should declare capability contracts.

Example:

```yaml
provides:
  - conversation
  - intent_extraction
  - recipe_generation
  - tool_calling
  - nutrition
  - ocr

requires:
  - text_generation
  - structured_extraction
  - policy_checking
```

The runtime should reject incompatible combinations before execution.

Capability contracts should define:

- provided capabilities
- required capabilities
- input modalities
- output schemas
- safety policies
- compatible runtimes
- compatible base model families

### Execution Planner

Runtime should include an execution planner. Not every request requires inference.

```text
User Request
  -> Planner
  -> Deterministic Path | SLM Path | Tool Path | Hybrid Path
```

Examples:

```text
"What is GST?"
  -> knowledge lookup
```

```text
"Show all vegan dishes"
  -> structured query
```

```text
"Compare these two dishes for a lactose-intolerant customer"
  -> knowledge lookup + SLM response composition + safety policy
```

The planner should reduce latency, cost, and hallucination risk by avoiding model calls when deterministic resolution is enough.

### Cost-Based Planning

Borrowing from compilers and databases, the planner should estimate cost and choose the cheapest strategy that satisfies the request.

Possible strategies:

- JSON lookup
- structured query
- knowledge graph traversal
- embedding search
- SLM inference
- hybrid plan

Cost dimensions:

- latency
- memory
- model size
- token cost
- confidence
- policy risk
- tool-call risk
- availability of deterministic answer

### Multi-Agent Composition

Runtime should support composition of small specialized agents rather than assuming one large agent.

```text
Conversation Agent
  -> Planner
  -> Knowledge Agent
  -> Tool Agent
  -> Safety Agent
  -> Response Composer
```

Each agent may use a different model, prompt, adapter stack, or deterministic tool if needed.

The platform should treat this as composition of capabilities, not a hardcoded agent framework.

### Adaptation Levels

The platform should optimize for targeted domain adaptation, not full training.

| Level | What changes | Cost | Recommendation |
|---|---|---|---|
| Prompt engineering | system prompts | very low | use first |
| Structured knowledge | RAG, JSON, graph, files | very low | use first |
| Partial fine-tuning | LoRA/QLoRA adapter weights | low | primary training path |
| Continued pretraining | domain language distribution | medium | only if needed |
| Full model training | entire model | extremely high | out of scope |

The default should be prompt and knowledge optimization first, then PEFT adapter training when measurable gaps remain.

### Knowledge Pack

A knowledge pack is the canonical model-independent representation of a domain.

Examples:

- `food`
- `banking`
- `healthcare`
- `retail`
- `legal`
- `education`

A knowledge pack contains:

- schemas
- entities
- relationships
- terminology
- policies
- validators
- ontologies
- examples
- synthetic generation rules
- provenance metadata

Knowledge packs must never depend on a specific base model, runtime, quantization format, or adapter.

### Adapter Pack

An adapter pack is a PEFT artifact produced from a knowledge pack, dataset, task, or customer-specific specialization.

Adapter examples:

- `food-lora`
- `menu-qa-lora`
- `recipe-lora`
- `allergen-lora`
- `restaurant-a-lora`
- `store-421-lora`

The platform should primarily publish adapters, not full models. Full merged model publishing is optional for deployment simplicity.

Adapter lifecycle:

```text
Knowledge
  -> CRAFT Blueprint
  -> Validation
  -> Synthetic Dataset
  -> Task Dataset
  -> LoRA/QLoRA Training
  -> Evaluation
  -> Quantization if needed
  -> Packaging
  -> Publish Adapter
```

### Runtime Pack

A runtime pack contains runtime-specific deployment assets.

Examples:

- GGUF
- Modelfile
- ONNX
- MLX
- CoreML
- metadata
- prompts
- tool definitions
- safety policies

Runtime packs are generated from adapter packs, base model metadata, prompts, and deployment target configuration.

### Stackable Adapters

The platform should support adapter layering where the runtime allows it.

Example:

```text
Base Model
  + Food Adapter
  + English Adapter
  + Hinglish Adapter
  + Restaurant Adapter
  + Allergen Adapter
```

Multi-stage specialization:

```text
General Model
  -> Domain Training
  -> Task Training
  -> Customer Training
```

Food example:

```text
Qwen
  -> Indian Food
  -> Restaurant Assistant
  -> Pizza Hut
  -> Store #421
```

The goal is to avoid shipping a new 400-500 MB model for every customer. A shared base model can be reused with small adapter packs:

```text
Base model: 350 MB
Food adapter: 20 MB
Restaurant adapter: 5 MB
Menu adapter: 8 MB
Allergen adapter: 4 MB
```

Applications combine the adapters needed for the active use case.

Future CLI shape:

```bash
sdk adapter create
sdk adapter train
sdk adapter evaluate
sdk adapter merge
sdk adapter publish
```

### Knowledge Compiler and IR

The platform should behave like a compiler.

```text
Knowledge Source
  -> Parser
  -> Semantic Validation
  -> Intermediate Representation
  -> Optimizer
  -> Dataset Generation
  -> Adapter Training
  -> Packaging
  -> Runtime
```

The intermediate representation is important because the same source knowledge should generate:

- datasets
- documentation
- APIs
- JSON
- knowledge graphs
- embeddings
- benchmarks
- runtime assets

All downstream stages consume the IR instead of raw files.

Example:

```text
Excel | Markdown | PDF | JSON | CSV
  -> Knowledge IR
  -> datasets, adapters, docs, APIs, graphs, embeddings, runtime packs
```

### Deterministic vs AI Stages

Separate deterministic processing from AI generation:

```text
Deterministic
  -> parser
  -> validation
  -> normalization
  -> knowledge graph

AI
  -> synthetic generation
  -> adapter training
  -> model evaluation
```

If an artifact changes, the manifest should make it clear whether the cause was deterministic source processing, prompt changes, generation model changes, or adapter training.

### Resumable Pipeline

Every stage should be independently runnable and cacheable:

```bash
sdk ingest
sdk normalize
sdk enrich
sdk blueprint
sdk generate
sdk train
sdk evaluate
sdk package
sdk publish
```

No stage should require rerunning the full pipeline unless its dependencies changed.

### Provenance

Every generated artifact should record:

- dataset version
- knowledge version
- blueprint version
- prompt version
- adapter version
- base model version
- SDK version
- commit SHA
- build time
- generation model, when synthetic data is used
- quantization target, when packaging is used

### Runtime and Model Agnosticism

The SDK must not be locked to one runtime, quantization format, model provider, or deployment target.

Training and research can happen through Hugging Face Transformers, but deployment should be selectable:

```text
Training Layer
  -> Hugging Face models and local datasets
  -> fine-tuning
  -> quantization pipeline
  -> GGUF | ONNX | MLX | Safetensors
  -> llama.cpp | Ollama | CoreML | HF Transformers | ONNX Runtime | vLLM
```

This makes one domain pack deployable across commodity CPUs, Apple Silicon, NVIDIA GPUs, Android devices, local browser wrappers, and future cloud serving.

### Model Backend

A model backend describes how the platform targets a foundation model family.

Initial model backend families:

- Qwen
- Gemma
- Phi
- Llama
- Mistral

The user-facing training API should eventually allow:

```bash
sdk train --model qwen2.5-0.5b
sdk train --model gemma3-1b
sdk train --model phi4-mini
sdk train --model llama3.2-1b
```

Changing model backend should not require domain-pack code changes.

### Runtime Adapter

A runtime adapter describes how packaged artifacts run.

Initial runtime adapters:

- `llamacpp`
- `ollama`
- `transformers`
- `mlx`
- `onnx`
- `vllm`

Runtime adapters must implement the common inference API. Applications should never call Ollama, llama.cpp, MLX, ONNX Runtime, or vLLM directly.

Common inference API:

```text
InferenceEngine
  generate()
  embed()
  classify()
  extract()
  tool_call()
  rerank()
  stream()
```

Runtime implementations:

```text
LlamaCppEngine
OllamaEngine
TransformersEngine
MLXEngine
ONNXEngine
VLLMEngine
```

Runtime responsibilities:

- load model artifact
- apply system prompt or runtime prompt bundle
- run inference
- expose streaming or batch mode
- report latency and memory
- surface model/runtime errors consistently

Recommended runtime posture:

- `llama.cpp`: default offline runtime because it spans Mac, Linux, Windows, Raspberry Pi, Android, CPU, Metal, CUDA, and Vulkan.
- `Ollama`: ready-to-run local developer experience.
- `Transformers`: training, evaluation, notebooks, and research.
- `MLX`: optimized Apple Silicon path.
- `ONNX Runtime`: Android, Windows, edge, and industrial hardware.
- `vLLM`: future high-concurrency server deployment.

### Publisher Plugin

Publishing should be a plugin system:

```bash
sdk publish huggingface
sdk publish ollama
sdk publish github
sdk publish local
```

Future publisher targets:

- Hugging Face Hub
- Ollama registry
- GitHub Releases
- local artifact registry
- enterprise registry

Hugging Face should be the primary publishing platform for open and collaborative assets:

- datasets
- domain packs
- LoRA adapters
- merged models
- GGUF models
- benchmarks
- evaluation reports
- model cards

Example namespace:

```text
huggingface.co/developerscoffee/Food-SLM-0.5B
huggingface.co/developerscoffee/Food-LoRA

```

### Capability Registry

The SDK should maintain a capability registry independent of domain packs. A domain pack declares which capabilities it needs; the SDK composes pipelines from those capabilities instead of hardcoding domain logic.

Initial capabilities:

- `conversation`
- `classification`
- `structured_extraction`
- `generation`
- `retrieval`
- `tool_calling`
- `summarization`
- `qa`
- `text_to_query`
- `citation`
- `policy_checking`
- `response_composition`
- `translation`
- `embedding`
- `reranking`
- `vision`
- `speech`

Example:

```yaml
domain: food_menu
capabilities:
  - conversation
  - structured_extraction
  - tool_calling
  - qa
  - policy_checking
```

The food domain is then just the first pack using these generic capabilities. A banking pack, healthcare pack, or retail pack should be able to reuse the same capability primitives with different knowledge, policies, validators, and benchmarks.

### Domain Pack

A domain pack is the installable distribution unit for a domain. It can include a knowledge pack, adapter configurations, prompt packs, validators, benchmarks, recipes, and runtime policies.

Examples:

- `food_menu`
- `indian_splitwise`
- `java_sonar`
- `enterprise_search`
- `prompt_enhancement`
- `release_text_to_sql`

Each domain pack should define:

- domain objective
- required capabilities
- knowledge pack metadata
- adapter pack recipes
- raw data sources
- canonical knowledge schema extensions
- task definitions
- prompt blueprints
- output schemas
- synthetic data recipe
- training config
- evaluation suite
- runtime contract
- safety policy
- packaging targets

Standard domain pack layout:

```text
food/
  metadata.yaml
  schemas/
  datasets/
  enrichment/
  synthetic/
  prompts/
  validators/
  benchmarks/
  recipes/
  evaluation/
  packaging/
```

Every domain pack should follow this shape so the SDK can discover and run the same stages without domain-specific branching.

Training generates adapter packs from domain pack recipes:

```text
food-pack
  -> food-lora
  -> menu-qa-lora
  -> allergen-lora
  -> restaurant-specific-lora
```

### Domain Marketplace

Domain packs should eventually be installable and versioned artifacts:

```bash
slm install food
slm install banking
slm install healthcare
slm install retail
```

A domain pack contains:

- schemas
- knowledge builders
- enrichers
- synthetic generators
- validators
- benchmarks
- runtime plugins
- safety policies
- sample configs

The marketplace concept keeps domain expertise modular. The SDK owns the lifecycle; domain packs own domain semantics.

Marketplace install should be independent from model install. A domain pack can be installed first, then trained or paired with a compatible published model later.

### Plugin Discovery

The SDK should discover plugins instead of requiring manual registration.

Plugin types:

- `ModelAdapter`
- `RuntimeAdapter`
- `Publisher`
- `DomainPack`
- `DatasetBuilder`
- `Validator`
- `Benchmark`
- `Generator`
- `Connector`

Expected CLI shape:

```bash
sdk plugins list
sdk plugins install <plugin>
sdk plugins remove <plugin>
```

Plugin discovery keeps the platform extensible without modifying SDK core for every new runtime, model, domain, connector, or benchmark.

### Task

A task is one trainable behavior inside a domain pack.

Food examples:

- menu ingredient query to JSON intent
- allergen query to database lookup intent
- recipe request to structured recipe plan
- kitchen command to pending automation payload

Finance examples:

- informal expense text to command JSON
- receipt OCR to receipt JSON
- spend question to read-only SQL

Java/Sonar examples:

- Java snippet to severity label
- Git diff to review risk summary
- Sonar issue to remediation plan

### Datastore

The datastore is a deterministic local or remote source of truth. The SDK should support file-based stores first, then database connectors later.

Initial datastore types:

- JSON file
- JSONL corpus
- CSV or Excel import
- SQLite

Future datastore types:

- PostgreSQL or YugabyteDB
- Jira API
- Confluence API
- Bitbucket API
- vector index

### Canonical Knowledge

Canonical knowledge is the domain-normalized representation built from raw data before artifact generation. It is distinct from raw source data, training examples, adapters, prompts, and runtime assets.

Required flow:

```text
Raw Data
  -> Canonical Knowledge
  -> Domain IR
  -> Generated Artifacts
```

This separation allows the platform to regenerate datasets, documentation, embeddings, adapters, benchmarks, APIs, or runtime packs when blueprints, prompts, validators, or target capabilities change without rewriting source knowledge.

The knowledge graph or canonical knowledge pack should be reusable across multiple models, prompt versions, and dataset generations.

### Common Object Model

The SDK should define a common object model that can represent many domains:

- `Entity`
- `Relationship`
- `Attribute`
- `Constraint`
- `Action`
- `Policy`
- `Validator`

Examples:

- A food dish is an `Entity`.
- A bank account is an `Entity`.
- A medical condition is an `Entity`.
- A product is an `Entity`.
- An allergen rule, banking policy, or dosage rule is a `Policy`.
- A kitchen automation command or payment settlement command is an `Action`.

Domain packs may extend this model, but they should not replace it.

### Dataset Version

Datasets should be treated like software releases.

Example:

```text
Food-Dataset
  v1.0
  v1.1
  v2.0
```

Each dataset release should include:

- metadata
- source information
- generated artifacts
- benchmark results
- reproducibility manifest
- validation report

### Prompt Pack

Prompts deserve versioning independently from datasets and model weights.

Prompt pack layout:

```text
prompts/
  router/
  extraction/
  qa/
  synthesis/
  evaluation/
  safety/
```

This allows prompt changes to be tested without retraining a model and model changes to be evaluated without rewriting prompts.

### Artifact Manifest

Every build should produce a manifest for reproducibility:

```yaml
model:
  name:
  version:
base_model:
adapter:
dataset:
knowledge_pack:
benchmark:
runtime_targets:
quantization:
license:

```

The manifest is the authoritative bill of materials for a trained or packaged artifact.

The v1 platform can be text-only, but the SDK should avoid assumptions that block multimodal support.

Future modalities:

- text

- documents
- audio
- video

- menu image understanding

Initial and future connector targets:

- filesystem
- JSON

## Compiler Lifecycle

### 1. Ingest

Convert raw files and APIs into normalized domain records.

Food v1 input:

```text
data/raw/Zomato_Menu_Scraped.xlsx
```

Normalized record shape:

```json
{
  "source_id": "zomato:row:123",
  "entity_type": "menu_item",
  "restaurant_name": "Example Cafe",
  "category": "Main Course",
  "item_name": "Paneer Butter Masala",
  "price": 320
}
```

### 2. Clean

Normalize and clean source records before domain enrichment.

Cleaning responsibilities:

- remove duplicates
- normalize IDs
- normalize dates, prices, and units
- preserve source references
- flag missing required fields
- produce source quality reports

### 3. Compile Domain IR

Convert cleaned records into canonical objects:

```text
Entity
Relationship
Attribute
Constraint
Action
Policy
Validator
```

Food example:

```text
Zomato row -> Entity(menu_item) + Attributes(price, category, restaurant)
```

Finance example:

```text
receipt OCR -> Entity(transaction) + Attributes(amount, merchant, currency)
```

Java/Sonar example:

```text
Sonar issue -> Entity(code_issue) + Attributes(rule_key, severity, file_path)
```

Knowledge generation is separate from model training:

```text
Knowledge Builder
  -> Knowledge Validation
  -> Knowledge IR
  -> Synthetic Dataset
  -> Fine-tuning
  -> Evaluation
```

### 4. Optimize IR

Apply compiler-style passes to improve the IR before artifact generation.

Optimization passes:

- entity resolution
- duplicate removal
- terminology normalization
- relationship expansion
- policy injection
- validation rule expansion
- source provenance linking

### 5. Enrich

Attach domain-specific metadata.

Food enrichment:

- dish ID
- ingredients
- allergens
- dietary tags
- spice level
- substitutions
- vendor/brand notes
- kitchen automation steps

Important design decision: enrichment quality controls answer quality. The SLM must not invent this layer.

### 6. Blueprint

Build or select CRAFT blueprints before synthetic generation. The blueprint becomes the source of truth for how knowledge is transformed into task examples.

Blueprint responsibilities:

- define task objective
- define retrieval strategy
- define output schema
- define validation rules
- define negative examples
- define coverage expectations

### 7. Generate

Generate task-specific examples from few-shot examples, blueprints, and canonical knowledge.

Recommended strategy:

- use CRAFT-style corpus retrieval and augmentation
- use blueprint-guided prompts
- generate diverse user phrasings
- preserve source references
- validate outputs immediately

Generated files:

```text
data/processed/<domain>/<task>_train.jsonl
data/processed/<domain>/<task>_val.jsonl
reports/<domain>/<task>_generation_report.json
```

### 8. Validate

Run validation before fine-tuning. Generated data that fails validation should be rejected or routed to manual review.

Validator hierarchy:

- SDK validators
- domain validators
- runtime validators

SDK validators:

- schema validity
- required fields
- duplicate detection
- source reference integrity
- train/validation leakage checks

Domain validators:

- food allergens and ingredient grounding
- banking policy and read-only query rules
- healthcare code validity such as ICD or medication constraints
- legal citation and jurisdiction constraints

Runtime validators:

- hallucination detection
- policy compliance
- response completeness
- tool-call safety
- structured output parseability

### 9. Train Adapter

Train only after prompt-template search and dataset validation are complete.

Supported adaptation modes:

- no fine-tune, blueprint prompt only
- LoRA
- QLoRA
- distilled task model
- optional continued pretraining only when domain language gaps justify it

Food model target:

- max artifact size: 500 MB
- likely base: `Qwen2.5-0.5B-Instruct` or `SmolLM2-360M`
- runtime format: GGUF Q4 or similar

Primary training output:

```text
adapter pack
```

Merged models are secondary deployment artifacts.

### 10. Quantize

Quantization is a first-class lifecycle stage, not only a packaging detail.

The SDK should support multiple target formats:

- GGUF
- ONNX
- MLX
- Safetensors
- TensorRT
- CoreML

The target format should be selected per deployment environment.

### 11. Evaluate

Every task must define validators before training starts.

Common validators:

- JSON validity
- required fields
- enum values
- no hallucinated entity IDs
- datastore lookup success
- safety policy compliance
- latency and artifact size

Food validators:

- dish ID exists in datastore
- allergen answer always includes disclaimer
- automation command requires approval
- ingredient claims exist in datastore
- response does not invent unavailable menu items

Finance validators:

- amount arithmetic
- SQL read-only
- schema validity

Code review validators:

- severity accuracy
- macro-F1
- explanation rubric

### 12. Package

Package base model references, adapter packs, knowledge packs, prompt packs, benchmarks, and runtime assets together.

Package contents:

```text
base_model/
  reference-or-manifest
adapters/
  adapter-pack
knowledge/
  knowledge-pack
domain/
  schemas/
  prompts/
  safety_policy.yaml
  eval_report.json
runtime/
  model_runtime_config.yaml
packaging/
  model_card.md
  license
  metadata.json
  benchmark.json
```

Food packaging target:

- quantized model under 500 MB
- local JSON datastore
- browser-accessible local runtime
- no hosted database required for v1

One command should eventually produce all configured deployment formats:

```text
sdk package
  -> GGUF
  -> Ollama bundle
  -> ONNX
  -> MLX
  -> Safetensors
  -> model card
  -> license
  -> benchmark report
  -> metadata
```

For Ollama packaging, the SDK should generate:

- `Modelfile`
- GGUF artifact
- system prompt
- metadata
- license
- examples

Example future command:

```bash
sdk package ollama
```

### 13. Runtime

The runtime contract should be consistent across domain packs:

```text
user input -> SLM structured output -> validator -> datastore/tool call -> response formatter -> final answer/action
```

The SLM should not directly execute side effects.

Runtime should be treated as another SDK module:

```text
Runtime
  -> Execution Planner
  -> Intent Engine
  -> Tool Router
  -> Knowledge Resolver
  -> Context Manager
  -> Safety Layer
  -> Response Composer
```

Model responsibility:

- infer intent
- produce structured output
- compose bounded natural language from resolved context

Non-model responsibility:

- plan deterministic, model, tool, or hybrid execution
- retrieve knowledge
- enforce policy
- validate tools
- execute safe actions
- append required disclaimers
- decide whether human approval is required

## Platform Module Design

All major stages should be pipeline plugins. A plugin exposes the same conceptual interface regardless of domain:

```text
input artifact + config + context -> output artifact + report
```

Pipeline plugin stages:

- ingestion
- cleaning
- compiler passes
- knowledge building
- enrichment
- synthetic generation
- validation
- fine-tuning
- quantization
- evaluation
- packaging
- runtime

### `ddl`

Responsibilities:

- parse domain definition language files
- validate domain declarations
- generate schemas, validators, docs, benchmarks, and prompt scaffolds
- compile DDL into Domain IR

### `ingestion`

Responsibilities:

- read raw domain files
- normalize source records
- preserve source IDs
- generate import quality reports

Food v1 needs Excel ingestion from Zomato workbook.

### `cleaning`

Responsibilities:

- normalize raw records
- deduplicate
- detect missing fields
- preserve provenance
- produce quality reports

### `knowledge_builder`

Responsibilities:

- convert clean records into canonical knowledge objects
- manage `Entity`, `Relationship`, `Attribute`, `Constraint`, `Action`, and `Policy`
- keep domain knowledge independent from training datasets
- support regeneration of training data from stable knowledge snapshots
- emit Knowledge IR

### `compiler`

Responsibilities:

- orchestrate parser, normalizer, resolver, validator, optimizer, and artifact-generation passes
- maintain pass cache
- enforce pass dependency graph
- expose Domain IR as a stable contract

### `ir`

Responsibilities:

- define Domain IR schema and versioning
- provide compatibility checks
- serialize and deserialize immutable IR artifacts
- support downstream consumers such as generators, benchmarks, packagers, and runtime exporters

### `datastore`

Responsibilities:

- define datastore schemas
- load local JSON/JSONL/SQLite
- resolve entity IDs
- return grounded facts

Food v1 should start with local JSON.

### `capabilities`

Responsibilities:

- register reusable capability definitions
- declare required input/output shapes
- map capabilities to pipeline tasks
- allow domains to reuse training and evaluation patterns

### `blueprints`

Responsibilities:

- store reusable task blueprints
- support prompt-template variants
- record winning template per model and task

### `synthetic`

Responsibilities:

- create synthetic JSONL examples
- use CRAFT-style retrieval from real corpora
- deduplicate and filter samples
- produce generation reports

### `training`

Responsibilities:

- manage LoRA/QLoRA configs
- call underlying training framework
- produce adapter packs
- track adapter artifacts and provenance

This repo already has early training CLI scaffolding. The platform design should generalize it into adapter-oriented domain adaptation.

### `evaluation`

Responsibilities:

- run task validators
- create eval reports
- compare prompt-only vs fine-tuned outputs
- gate publishing
- run domain-independent benchmarks

### `benchmarking`

Responsibilities:

- run common model and pipeline benchmarks independent of domain
- compare prompt-only, fine-tuned, and quantized variants
- generate regression reports

Common benchmark dimensions:

- accuracy
- latency
- memory
- hallucination rate
- tool-call accuracy
- structured output accuracy
- policy compliance
- package size

Benchmark packs should be modular:

```text
benchmarks/
  latency/
  memory/
  hallucination/
  extraction/
  json/
  multilingual/
  reasoning/
  tool_call/
```

Each domain can add benchmarks, but SDK-level benchmark packs provide a shared baseline.

### `packaging`

Responsibilities:

- prepare model artifacts
- attach domain pack files
- produce local-runtime config
- publish to Hugging Face or local registry
- export to GGUF, ONNX, MLX, Safetensors, TensorRT, or CoreML targets

### `registry`

Responsibilities:

- install and resolve knowledge packs, blueprints, prompt packs, adapters, runtime packs, benchmarks, validators, plugins, and connectors
- enforce version compatibility
- support local, Hugging Face, GitHub, enterprise, and filesystem-backed registries

### `publishing`

Responsibilities:

- publish datasets, models, adapters, benchmarks, and domain packs
- support registry-specific metadata
- create or update model cards
- upload benchmark and evaluation reports
- publish to Hugging Face, Ollama, GitHub Releases, local registry, or enterprise registry

### `runtime`

Responsibilities:

- run inference through Ollama, llama.cpp, ONNX, or Transformers
- validate structured output
- query datastore/tool
- format response
- enforce safety policy

Runtime submodules:

- execution planner
- intent engine
- tool router
- knowledge resolver
- context manager
- safety layer
- response composer

### `planner`

Responsibilities:

- choose deterministic, model, tool, or hybrid execution
- estimate cost across lookup, graph traversal, embedding search, SLM inference, and tool calls
- reject plans that violate capability contracts or safety policies
- emit explainable execution plans for debugging

### `prompts`

Responsibilities:

- version prompt packs
- store router, extraction, QA, synthesis, evaluation, and safety prompts
- run prompt-only evaluations
- compare prompt revisions independently from model revisions

### `knowledge`

Responsibilities:

- build canonical knowledge packs
- validate knowledge quality
- version knowledge snapshots
- make knowledge reusable across models and datasets
- produce and consume Knowledge IR

### `connectors`

Responsibilities:

- read from filesystems, databases, object stores, APIs, and enterprise document systems
- normalize connector outputs into SDK artifacts
- keep pipeline stages independent from data-source specifics

## Food Menu Domain Pack v1

### Objective

Build a sub-500 MB local Indian food assistant for:

- deep menu ingredient Q&A
- restaurant chatbot
- recipe generation
- kitchen automation translation

### Architecture

```text
Browser or edge device
  -> Local runtime server
  -> Quantized GGUF model under 500 MB
  -> Intent JSON
  -> Local JSON food datastore
  -> Grounded response or pending automation payload
```

### Initial Runtime Decision

Preferred first runtime targets:

- GGUF quantized model
- Ollama or llama.cpp
- browser UI against local runtime
- JSON datastore converted from Zomato workbook and enriched specs

This is a reference deployment choice, not an SDK constraint. The same food pack should later package to ONNX, MLX, Safetensors, and other targets.

### Food Intent Schema

```json
{
  "intent": "database_query | kitchen_automation | recipe_generation | clarification",
  "target_dish_id": "string_or_null",
  "specific_parameters": ["allergens", "deep_ingredients", "spice_level", "brand_vendors", "substitutions", "automation_steps"],
  "user_raw_ingredients": [],
  "requires_human_approval": true
}
```

### Food Safety Policy

- The model must never guess ingredients.
- All ingredient and allergen claims must come from datastore fields.
- Allergen responses must include a medical/staff-confirmation notice.
- Kitchen automation always returns pending approval, never direct execution.
- Unknown dishes or ambiguous dish names trigger clarification.

### Food Datastore Schema

Minimum v1 food entity mapped onto the common object model:

```json
{
  "entity": {
    "id": "paneer_butter_masala",
    "type": "menu_item",
    "display_name": "Paneer Butter Masala"
  },
  "attributes": {
    "restaurant_name": "Example Restaurant",
    "category": "Main Course",
    "price": 320,
    "dietary_tags": ["vegetarian"],
    "spice_level": "medium",
    "allergens": ["dairy", "cashews"],
    "deep_ingredients": {
      "base_components": ["tomatoes", "cashew paste", "kashmiri red chili", "kasuri methi"],
      "brand_vendors": ["Amul butter"],
      "substitutions": ["cashew-free gravy available only if explicitly configured"]
    }
  },
  "actions": [
    {
      "type": "kitchen_automation",
      "approval_required": true,
      "steps": []
    }
  ],
  "policies": ["allergen_disclaimer_required", "automation_human_approval_required"]
}
```

### Food Training Tasks

- Query to intent JSON
- Hinglish query to intent JSON
- Ambiguous query to clarification JSON
- Allergen query to safe database lookup JSON
- Kitchen command to pending automation JSON
- Loose ingredients to recipe-generation plan JSON

### Food Evaluation Gates

Food v1 should not ship unless:

- model artifact is under 500 MB
- JSON validity is above target threshold
- dish lookup success is above target threshold
- allergen disclaimer injection is deterministic
- kitchen automation never bypasses approval
- generated ingredient claims match datastore

## Long-Term Vision

The platform should be a compiler for domain intelligence. It should be closer to LLVM for domain AI artifacts or OpenAPI for service contracts than a one-off training script.

```text
Developer
  -> Knowledge Sources
  -> Knowledge Compiler
  -> Domain IR
  -> Optimization
  -> Artifact Generation
      -> Adapter Packs
      -> Runtime Packs
      -> Prompt Packs
      -> Knowledge Graph
      -> Embeddings
      -> Benchmarks
      -> Documentation
      -> APIs
      -> Validators
  -> Registry
      -> Hugging Face
      -> Ollama
      -> GitHub Releases
      -> Local Registry
      -> Enterprise Registry
```

The food menu domain remains the first reference implementation. It should validate that the platform can compile knowledge once, generate datasets, train adapters, evaluate consistently, package to multiple runtimes, and publish artifacts without binding the platform to any one model or inference stack.

At full maturity, SLM training becomes one output of the platform rather than its defining purpose.
